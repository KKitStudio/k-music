# 04 技术选型与跨平台策略

> 候选方案对比、推荐结论、网易云接口选型、跨平台路线与合规要点。
> **结论已冻结**：Rust 核心 + Tauri(Material Web) GUI 壳；CLI 并行供 headless 运维。

## 1. 候选技术方案对比

| 方案 | 核心栈 | PC | 飞牛(NAS) | 安卓 | 评价 |
|---|---|---|---|---|---|
| **A. Rust 核心 + Tauri GUI（已选）** | Rust crate + Tauri(WebView) | ✅ 原生、5–15 MB | ✅（交叉编译 Linux） | △（Tauri 移动端较新） | 小又快、Material Web、零运行时 |
| B. Python + CLI | Python 3.11 + Typer | ✅（解释器常在） | ✅（原生 Python） | △（Termux） | 生态好但打包 15–30 MB、非原生 UI |
| C. Node + Electron | Node + Electron | ✅ | △（重） | △ | **120–250 MB，违背"小又快"，排除** |
| D. Flutter / Dart | Dart | ✅ | ✅(Linux) | ✅（原生） | Material 原生+安卓强；细分生态薄，备选 |
| E. 纯 C | C | ✅ | ✅ | ✅ | 极小但开发慢、易 bug，仅用于扩展转换器 |

### 1.1 UI 设计语言：Material Design（Q6 已确认）
- 统一视觉/交互规范，组件可在 Web / 桌面 / 移动端复用。
- 官方实现以 **Web（Material Web）** 与 **Android（Material Components）** 为主；桌面端用「Web 前端嵌入 WebView」实现（Rust+Tauri 正合适）。本方案选 Tauri + Material Web 组件，不打包 Chromium，既满足 Q6 又保持"小"。

### 1.2 核心语言选型对比（Python / C / Rust / Node.js）
本应用是 **I/O 密集型**（下载、扫描、SQLite），性能非瓶颈；选型优先级：**开发效率、生态契合、跨平台前景（飞牛=Linux/安卓）、Material UI 承载方式**。

| 维度 | Python | C | Rust | Node.js |
|---|---|---|---|---|
| 开发效率 | ★★★★★ | ★ | ★★★ | ★★★★ |
| 运行性能 | ★★★ I/O 够用 | ★★★★★ | ★★★★★ | ★★★ |
| 跨平台/发行 | ★★★★ 需带运行时/打包 | ★★★★ 无运行时但需自建基建 | ★★★★★ 单文件静态、交叉编译一流(含 Android) | ★★★ 需 Node 运行时/pkg |
| 音频元数据 | ★★★★★ mutagen | ★★ 自接 taglib | ★★★★ lofty | ★★★ music-metadata |
| 网易云 HTTP | ★★★★★ httpx | ★★ libcurl 自封 | ★★★★ reqwest | ★★★★ axios |
| SQLite | ★★★★★ 标准库 | ★★★ C API | ★★★★ rusqlite | ★★★ better-sqlite3 |
| 调用 NCM 工具 | ★★★★ subprocess/ctypes | ★★★★★ 直接 C ABI | ★★★★ FFI 调 C ABI | ★★★ ffi-napi |
| 承载 Material UI | ★★★★ 后端+Web | ★★ 自搭 | ★★★★★ Tauri+Material Web | ★★★★ Electron/MUI |
| 适合本项目的角色 | 备选（若已熟、求快） | 仅扩展转换器本身 | **核心已选** | Web/UI 层可选 |

### 1.2.1 补充候选：Flutter / Dart（Material 原生 + 强 Android）
当用户选定 Rust 核心后，若未来安卓是**近期硬需求**且要求 Material **最正宗还原**，Flutter 是值得正视的替代 UI 壳：

| 维度 | Rust + Tauri | **Flutter (Dart)** |
|---|---|---|
| Material 还原度 | Web 组件，近似 | **原生一等公民** |
| 安卓成熟度 | Tauri 移动端较新 | **原生成熟** |
| 单代码库 | 桌面/移动分壳 | **PC+安卓+Linux 一套** |
| 分发体积 | 5–15 MB | 10–30 MB（仍"小"） |
| 生态（netease/ncmdump） | 强（reqwest/rusqlite/FFI） | 较弱（Dart 细分小众） |

**取舍**：Flutter 在安卓与原生 Material 上更强，代价是二进制略大、Dart 生态薄。本设计**核心与 UI 解耦**，届时换 Flutter 壳贴同一核心即可，无需重写逻辑。

### 1.2.2 推荐架构姿势：Rust 核心 + 可替换 UI 壳（已采纳）
1. **Rust 实现核心逻辑层**（小、快、零运行时、FFI 调 libncmdump 与 netease 协议顺手）。
2. **核心 UI 无关**：通过清晰模块边界 + 本地 API/HTTP 对外暴露能力，不依赖任何 GUI 框架。
3. **UI 壳可替换**：PC 阶段 Tauri(Material Web)；安卓阶段可换 Flutter/Compose 贴核心。
4. **不焊死安卓 UI 框架**：保持核心解耦即可进可攻退可守。

### 1.3 分发体积与运行时速度对比（目标：小又快）

> I/O 密集型，**执行速度四者几乎无差别**（瓶颈在网络/磁盘）。"快"体现为启动延迟与开发/构建速度；"小"体现为分发体积（对 NAS/安卓敏感）。

| 形态 | 分发体积 | 冷启动 | 部署依赖 |
|---|---|---|---|
| C 静态 | 0.3–2 MB | <5 ms | 仅 libc |
| Rust CLI 静态 | 2–6 MB | <10 ms | 无 |
| **Rust + Tauri（Material Web）** | **5–15 MB** | 20–80 ms | 无（复用系统 WebView） |
| Python 打包(PyInstaller) | 15–30 MB | 60–150 ms | 内嵌解释器 |
| Node 打包(pkg) | 30–60 MB | 80–200 ms | 内嵌 Node |
| Node + Electron | 120–250 MB | 300–800 ms | 内嵌 Chromium+Node |

**结论**：
1. "小又快"冠军 = Rust(+Tauri)：5–15 MB、启动 <80 ms、零运行时、交叉编译一流。
2. Python 差距在打包体积/启动，自有 PC 上执行速度无感差异。
3. **Electron 务必排除**（120–250 MB）。
4. 飞牛/安卓上 Rust 的"小"由锦上添花变必需。

## 2. 网易云接口与库选型

- **接口协议**：复用社区维护的 `NeteaseCloudMusicApi` 请求协议（登录态、歌单、喜欢、下载 URL、参数加密）。
- **集成方式：内置封装（B）**：在 Rust 中直接实现所需端点（约 4–5 个）的请求构造与签名。优点：单进程、易部署、契合"小又快"；缺点：需自行跟进接口变动（接口层独立 + 单测覆盖缓解）。
- 不依赖外部常驻服务，降低部署负担。

## 3. 关键依赖（Rust 技术栈）

- `cargo` + stable Rust
- `clap`（CLI 子命令）
- `tokio` + `reqwest`（异步 HTTP）
- `rusqlite`（SQLite）
- `serde` + `toml`（`config.toml` 配置）
- `lofty`（音频元数据采集）
- `aes-gcm` / `rustcrypto`（登录态本地加密）
- `tauri` + Material Web（前端 SPA）
- `axum`（本地播放文件服务，支持 Range）
- （可选）`ffprobe`（冷门格式回退）

## 4. 跨平台适配策略

1. **路径与编码**：全程 `std::path::Path` / UTF-8，避免硬编码分隔符。
2. **子进程调用**：NCM 工具跨平台 `std::process::Command`；命令模板隔离差异。
3. **配置与数据**：分为两处——app 级配置 `<exe 目录>/kqk-app.toml`（应用设置 + 当前曲库路径）与曲库级数据 `<曲库根>/.mt/`（config.toml / library.db / app.log / tools/）；曲库数据随曲库走，便于整体迁移到 NAS（见 docs/05）。
4. **飞牛(NAS)**：交叉编译 Linux 二进制；如需远程访问，核心 API + 播放文件服务加鉴权后复用同一前端。
5. **安卓**：优先"核心不变 + 换/加 Flutter 壳"；Tauri 移动端亦可评估，但列为次选。

## 5. 合规与风险

- **版权 / 法律风险（重要，持续关注）**：
  - 「**不内置解密、仅调用外部工具**」降低本项目直接分发解密代码的风险，但**不能等同于零法律风险**：
    1. **规避技术措施风险**：NCM 属版权方技术保护措施，使用第三方工具解密在含中国《著作权法》及美国 DMCA §1201 等法域下可能触及「规避技术措施」条款；个人非商业备份/格式转换抗辩力度因法域而异。
    2. **工具二进制分发**：`tools/ncm/bin` 存放 ncmdump 可执行与 DLL；仓库**公开分享**即构成规避工具分发，风险上升；**仅本地个人使用**风险低得多。
  - **已采纳的缓释承诺（用户明确）**：① 绝不重新分发解密（转码后）音频；② 绝不公开分享 NCM 工具、对外发布 app 也**不内置**该工具（打包须排除 `tools/ncm/bin`）；③ 持续关注法规。
  - 上述承诺下实际法律风险已很低（个人非商业自用 + 不分发工具/产出）；发布若误带 bin 即触发分发风险。
  - **接口/合约风险（非版权）**：复用非官方接口可能违反服务条款，最坏后果为**账号受限/封禁**；已用扫码+登出+释放设备槽位做风控。
  - ⚠️ 工程视角提示，**非法律意见**；正式合规判断请咨询律师。实现中出现的法律风险点将**主动提示**。
- **接口稳定性**：接口层独立、单测覆盖，便于跟进变动。
- **账号安全**：登录态本地加密，日志不明文输出敏感信息。
- **配额**：仅用户侧上限保护，不试图绕过官方限制。

## 6. 决策记录（均已确认，详见 00 第 5 节）

- Q1 技术栈：**Rust 核心 + Tauri GUI 壳**（用户确认 Rust 路线，认同"小又快"）。
- Q2 登录：扫码 + 退出登录（释放设备槽位）。
- Q3 目录：顶层 `app/tools/release` 为项目源码与构建；曲库为用户指定的任意目录，应用数据收敛于其下隐藏目录 `.mt/`，由 app 级配置 `kqk-app.toml` 的 `last_library_dir` 定位。文件组织由 `config.library.file_scheme` 决定（默认 `artist_album`：`<artist>/<album>/<title>`；另 `album`/`artist`/`flat`）；NCM 原文件统一在 `download/ncm` 与 `download/pendingNcm`，旧顶层 `_ncm_raw/` 已废弃（见 docs/05）。
- Q4 NCM：不删原文件 + 单独存放 + 格式随原始 + 工具就绪即自动转换（无独立开关）。
- Q5 配额：优先服务端动态获取 + 回退（软上限/本月记录真值/服务端拒绝为权威）。
- Q6 UI：Material Design。
- 追加：配置格式 **TOML**；匹配 `clean_name_db`；升级 `ask` 批量确认；导入 copy/move；播放 Tauri Web + `<audio>` + localhost Range 服务。
- **Electron 排除**；**C 不用于应用核心**。
