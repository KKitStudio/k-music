# musicMT 真机验证方案（2026-10-28）

> 目的：在用户真实 PC 上验证此前仅经单元测试/loopback 冒烟覆盖的功能，补齐端到端证据。
> 本文件为「人工执行清单」。脚本/产物见 `docs/06_进展小结` 与 `target/release/`。
> 日志统一落盘到 `<曲库>/.mt/app.log`（GUI 模式下 stdout 不可见，诊断以该文件为准）。

## 0. 编译产物与一键启动

- 已新增 `mt-cli verify` 子命令（干跑网易云同步计划，不下载、不消耗配额）。
- **一键启动入口 = `dist/k_music.exe`**：双击即启动（自带后端 HTTP 服务 + 桌面窗口），**无需先开 CLI**。
- **入口命名（2026-11-06，TODO A3 已实施）**：crate 与构建产物仍为 `mt-gui.exe`（`target/release/`），发布目录由 `tools/package_gui.bat` 统一改名 `k_music.exe`，`mt-cli.exe` 不变。因此下方所有「双击 / 任务管理器进程名」均指 `k_music.exe`；运行时按 `current_exe()` 目录与命名互斥体工作，与文件名无关。
- 发布文件夹 `dist/` 内容：`k_music.exe`（主入口）、`mt-cli.exe`（命令行）、`frontend/`（前端静态资源）、`README.md`。
- 重新打包（Windows 双击即可）：`tools/package_gui.bat` —— 编译 release，把 `mt-gui.exe` 拷成 `dist/k_music.exe`、`mt-cli.exe` 原样拷入 `dist/`（并清理旧 `mt-gui.exe`）。**前端静态资源已由 `app/gui/build.rs` 在 `cargo build` 编译期自动同步到 `dist/frontend`**，bat 不再手动拷贝前端。
- 手动编译：`cargo build --release -p mt-cli -p mt-gui` —— 前端会由 `app/gui/build.rs` 自动同步到 `dist/frontend`；再把 `mt-cli.exe` 原样拷入 `dist/`、把 `mt-gui.exe` 拷成 `dist/k_music.exe` 即可（勿沿用旧名，否则出现两个入口）。

### 0.1 本次针对「双击打不开页面」的修复（已实地验证）
- **前端目录改为相对 exe 级联解析**：此前 GUI 入口把前端写死成 CWD 相对 `./app/gui/frontend`，双击时 CWD 是 `dist/` 找不到前端 → 页面空白。现 `serve::resolve_frontend_dir` 依次尝试 `exe\frontend`、`exe\app\gui\frontend`、`exe\..\..\app\gui\frontend`、`cwd\app\gui\frontend`，返回首个含 `index.html` 的目录。GUI 与 CLI 共用此逻辑。
- **端口回退**：`server.port` 默认 `0`（系统随机分配）；若绑定失败（旧实例未退出）自动回退随机空闲端口，避免 GUI 因 `expect` 僵死。
- **就绪等待**：开窗口前轮询后端端口至可连接（≤5s），避免 WebView 打开瞬间连不上。
- **验证**：从 `dist/` 起服务，`GET /` → HTTP 200 返回 `index.html`（9257B），`/api/status`、`/app.js` 均 200。

## 3. NCM 转换（需真实 .ncm 文件 + 工具）

> **新规则（2026-10-28）**：唯一开关是 `config::NcmConfig::tool_ready()`（工具路径存在且为文件）。
> **只要指定了工具，就自动走转换歌曲的逻辑**——下载落点、导入、散落 ncm 整理、以及 `pendingNcm` 积压，凡遇到 ncm 一律尝试转换（无工具才暂存 `pendingNcm`/跳过）。
> 已彻底移除 `enabled` 显式开关；运行期唯一判据为 `config::NcmConfig::tool_ready()`（工具路径存在且为文件）。

### 3.1 三种指定工具的时序（与 docs/05 §6.1 一致）

| 时序 | 描述 | 行为 |
|------|------|------|
| ① 初始化未指定 | 新建曲库时未指定工具 | 期间遇到的 ncm 暂存 `download/pendingNcm/` 不入库；后续任意时刻指定工具即可自动清积压 |
| ② 初始化即指定 | 新建曲库时「指定 NCM 工具」并选到有效 exe（或 `.mt/tools/` 下已检测到） | 此后所有 ncm（下载/导入/散落）均自动转换入库 |
| ③ 初始化未指定、之后指定 | 已运行的曲库在「设置/向导」里**事后**指定工具 | 触发 `process_pending_ncm`：自动把 `pendingNcm` 积压逐个转换入库（已实测：`POST /api/ncm-tool` 后 `pending_ncm:2→0`、`backlog.imported:2`） |

## 5. 执行顺序建议

1. 先跑 L1–L6（纯本地，秒级，必过）。
2. 跑 L8「从本地网易云音乐曲库更新」（本地增量导入，当前主同步路径，不联网）。
3. 网易云服务端验证（原 N1–N6）**已移除**，无联网验证步骤；主同步路径为 L8 本地导入。
4. C1–C3 与 P1–P5 穿插进行。
5. 每一步异常优先看 `<曲库>/.mt/app.log`；CLI 命令加 `> out.txt 2>&1` 留存 stdout。

## 6. 已知未决项（真机重点观察）

1. **rfd 原生目录框**：Tauri 2 的 axum worker 线程为 MTA，未初始化 COM，`rfd::FileDialog` 可能弹不出或返回 canceled。若 P4 失败，日志会有线索；修复方向：在主线程或改用 Tauri dialog API 调 `pick_folder`。
2. **封面外链回退**：无内嵌封面时当前返回 204，不回退网易云外链封面；待实现。
3. **切换曲库旧曲目**：仅文件缺失才孤儿清理；切换目录后旧目录曲目仍在 DB。若需「整库切换」需另加清空/重建选项。
4. **动态配额字段**：服务端配额相关项（原 `vip_download_count` 等）已随功能移除；未来基于官方开发者 API 恢复下载时再核实。
5. **升级策略确认 UI**：`quality.upgrade_policy=ask` 原为服务端音质升级交互（已随下载移除）；本地导入（FR-14）不进行音质升级，仅 copy 现有文件。待未来服务端下载恢复时再设计。
